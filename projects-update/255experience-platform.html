01What the platform actually is

Most 360° tour products are viewers with an upload form attached. 255Experience is the opposite: the viewer is deliberately thin, and nearly all of the engineering is in the Creator Studio — the authoring environment where a photographer's raw equirectangular panoramas become a navigable, branded, guided place.

That distinction drives every architectural decision below. A visitor should never load an authoring system; a creator should never hand-edit JSON. The two are joined by exactly one artefact — an immutable published manifest.

The vocabulary

These words mean specific things throughout the codebase and this document.

02The three surfaces

One codebase serves three audiences with almost no shared UI between them.

For the studio team

Creator Studio Strong beta

The authoring environment. Upload and correct panoramas, place markers, connect Scenes, direct Journeys, set branding, check health, publish. Four areas — Build, Experience, Review, Insights — matching how production actually proceeds.

For the visitor

Public Experience Beta

The place itself. Reads only a published manifest, never the authoring database. Welcome screen, panorama navigation, Discover Mode, Journeys, search, ambient audio.

For the paying client

Client Portal First version

A scoped view for the business the work is for: their Experiences, live links, headline numbers, and a feedback channel that writes review comments back into the Studio.

03The core architecture

Everything hangs off one decision: draft state and published state are different things, and the viewer only ever sees the published one.

STAGE 1
Draft

Mutable authoring state in the database. Only the Studio touches it.

STAGE 2
Validate

Health check. Errors block a publish; warnings do not.

STAGE 3
Compile

Draft becomes a manifest. Asset ids resolve to URLs; menus resolve to trees.

STAGE 4
Publish

Written to disk, snapshotted in manifest_versions, version bumped.

STAGE 5
Serve

The viewer reads the manifest. No database access, ever.

This is why the platform is unusually safe for its stage. A broken Studio cannot break a live Experience. A rollback is re-pointing at an earlier snapshot, not undoing edits. And because the manifest is self-contained, the viewer can eventually be served entirely from a CDN.

What "self-contained" means in practice

The compiler resolves everything the viewer would otherwise have to look up. Media asset ids become public URLs. A category-driven menu becomes a literal tree. A Scene-sourced Welcome panorama resolves through that Scene. A deleted asset resolves to an empty string rather than a broken link. 

experiences/{experience-id}/
├── versions/{version}/manifest.json   immutable, cache forever
└── live.json                          pointer, cache briefly

That layout is the target once object storage lands. Today the manifest is a file in content/ and the version history lives in the database.

Schema compatibility

Every field added to the manifest carries a default. A manifest published before a field existed still validates. This is what allows the schema to evolve without a migration of published content — and it is the single most important rule to keep.

04Build — constructing the place

Four sections: Scene Workspace, Structure, Connections, Media. The first is where most production time is spent.

Scene Workspace

One panorama on screen, one selected element, one relevant inspector. The creator stays here rather than hopping between pages that all describe the same Scene. A filmstrip along the bottom and a rail on the left switch Scenes; [ and ] step through without the mouse.

The editor renders the same markers the visitor sees, from the same code. Earlier it drew its own placeholder dots, which meant nobody saw the real design until preview.

Spatial elements

Navigation Points, Discover Points, Persistent Labels, Audio Points and Journey Cues share one model. Each stores only what it deliberately overrides; everything else inherits from the Experience theme, so re-branding moves every marker that never opted out.

  • Placement — surface, wall, floor, screen-facing, or free yaw/pitch/roll with depth offset.
  • Size — Small/Medium/Large presets plus an exact pixel value, 20–140px. The tap target never drops below 48px regardless of how small the drawn marker is.
  • Animation — seven presets with start conditions (always, Discover open, hover, near centre, Journey event, once per visitor) and stop conditions (after interaction, after first run, when visited, when another is selected).
  • Labels — eight visibility rules, nine positions, offset, wrapping, leader lines, and a collision priority.

Label visibility, animation triggers and label collision are evaluated at runtime against the live camera, in a module shared by the editor and the viewer. Labels flip away from screen edges and lower-priority labels are suppressed when they overlap.

Camera-stand cover

The tripod under the camera is hidden by a real rectangle on the floor — width, depth, scale, height offset, rotation, opacity, and edge softness feathered into the image's alpha channel. Adjustable numerically or by dragging corner handles in the panorama, both editing the same values.

Apply to…

Most settings repeat across a shoot. A scope — this Scene, selected Scenes, this Space, this category, the whole Experience — resolves to explicit targets, shows what will change before it happens, and returns previous values so the whole operation is a single undo.

Media

Uploads keep the original untouched. Every derivative — desktop 6144px, mobile 2048px, a blurred preview and a thumbnail — is re-derived from that original with the current adjustment recipe, so edits never compound.

Image Lab

Exposure, contrast, highlights, shadows, whites, blacks, saturation, temperature, HDR tone mapping, sharpness, denoise. Presets, custom saved looks, copy/paste between panoramas, and batch application.

The correctness rule

The six tone controls compose into a single curve, and the live preview derives its CSS from that same curve. Two independent approximations of "what does this slider do" is how a preview ends up lying to the creator. What CSS genuinely cannot show — HDR, sharpen, denoise, all spatial — is named explicitly rather than implied away.

Structure & Connections

Spaces and Scenes, categories, primary Scene selection. Connections are directional doorways with optional arrival views, so entering a room from the hall can face the sofa while entering from the kitchen faces the door back out. A reachability check flags Scenes no visitor could reach.

Thumbnails

Scene cards show a rectilinear render — the view a visitor would actually see — not the equirectangular source, which flattens into a stretched smear. Five card shapes are rendered at capture time, each at its own field of view so a portrait card frames the subject rather than showing a squeezed slice of a landscape frame.

05Experience — directing the visit

Entry Flow

The Welcome screen, audience selection and exploration choice. The Welcome background can be an image, a 360° panorama, a video, a brand gradient, or nothing — each with its own controls: focal point dragged directly on the preview, panorama starting view and auto-rotation, video poster, trimming, fades and mobile fallbacks.

The editor previews at three widths and in five states — ready, loading, slow network, autoplay blocked, reduced motion — using the real asset and the same style functions the public viewer renders from.

A deliberate override

Autoplay is forced muted at render time regardless of the stored setting, because browsers refuse autoplay with sound and honouring it would produce a video that silently never starts. The creator's intent is preserved in the data and surfaced as a warning in the editor.

Navigation

One menu structure, presented differently per device. The top level can be hand-built or derived from categories — with the derived form, adding a Space to a category puts it in the menu with no second edit, and it can never drift from the Spaces it describes.

Empty categories are hidden automatically and reported, because a heading vanishing from a menu otherwise looks like a bug. Uncategorised Spaces raise a pre-publish warning rather than a block — they remain reachable by connection, search and direct link.

Journey Director

The most distinctive part of the product. A Journey is a sequence of steps, each with camera keyframes, timed events, optional branches, narration and ambience. Three presentations — narrator card, compact audio player, or cinematic captions — and ambience ducking while narration plays.

The data model is fully built: journeys, steps, keyframes, events and branches are all first-class tables with a builder UI.

Brand & Spatial UI

Colours, chrome and the 255 Halo — one configurable SVG hotspot rather than a bespoke image per icon/colour/client combination. Accent, surface, icon colour, halo geometry, default size, label behaviour and animation, with per-role weighting so Navigate reads heavier than Discover.

06Review & publish

Experience Health

Validation produces a flat issue list; that rolls into per-category scores — Structure, Navigation, Media, Content, Accessibility — so a large Experience reads as "Structure 100% · Navigation 86%" rather than one opaque number. Errors block publishing. Warnings do not.

Alongside it, a production progress model turns raw state into human phases with completion percentages and a prioritised list of next actions — what makes a forty-Scene Experience feel manageable instead of a wall of errors.

Publishing

Compiles, validates, writes the manifest, snapshots it for rollback, bumps the content version. The public route never touches the Studio database; this is the only bridge, and it runs only on an explicit action.

Client feedback

Clients leave comments from the Portal; they appear in the Studio's Review section against the Experience. A real review loop, scoped so a client sees only their own work.

07Insights

Be precise about this one

The Client Dashboard shows deterministic sample data seeded from the Experience's real structure — actual Space and Journey names, stable across reloads, and labelled as sample in the UI. Real recorded events replace the visit, CTA and completion figures once any exist. Traffic sources, device breakdown and leads remain sample, because they need infrastructure that does not exist yet: user-agent parsing, referrer capture, and form submission.

The event collector itself is real and minimal — one row per event, no session identity. There are 238 recorded events in the current database. What is missing is the session layer: the thing that turns events into visits, unique visitors, engagement time, device mix, referrers and campaign attribution.

08The public viewer

Deliberately quiet. The panorama is the brightest thing on screen; chrome recedes until wanted.

  • Panorama rendering — Photo Sphere Viewer, wrapped behind a renderer-agnostic interface so a future engine can replace it without touching UI code.
  • Navigator — a relationship diagram of which Spaces connect to which, not a floor plan.
  • Space carousel — mostly image, one line of text; a spatial guide rather than a permanent nav bar.
  • Discover Mode — information markers appear only when asked for.
  • Focus Mode — camera glides to a subject, chrome drops away, one card remains.
  • Journey Mode — its own chrome, three presentations, narration and ducked ambience.
  • Search — across Spaces, Scenes, Discover Points and Journeys, grouped under category headings with filter chips.
  • Ambient audio — resolved by priority: Journey soundtrack over Space over Scene.

Known gap — the largest one

The Studio offers six desktop × six mobile navigation presentations and previews each one. The public viewer reads neither field. Every creator choice produces the same result. This is stored, published into the manifest, and used by menu health — but never rendered. It should be gated in the UI before any paying client sees it.

The important boundary is lib/studio/repository/. Every database access goes through it, which is what makes the Postgres migration a replacement rather than a rewrite.

Testing philosophy

Unit tests cover pure logic — tone curves, geometry, override resolution, search, menu derivation. The 47 verification scripts do something different: they drive the running system, in a real browser or against the real database, and check that a feature is actually connected rather than merely present.

Several bugs this year were "the setting persists but nothing reads it". Verification scripts exist specifically to catch that class.

Two deliberate JSON columns

Marker presentation overrides and Welcome media configuration are stored as validated JSON rather than columns. Both are purely presentational, always read and written as a whole, and differ by type — a wide flat row models that badly. Both are normalised on the way in and on the way out, so the renderer never sees a value it cannot honour, including from a manifest compiled by an older build.

Media on disk

206 MB across 18 experience folders. One panorama costs roughly 4.6 MB: a 2.3 MB original, a 2.2 MB desktop derivative, 214 KB mobile, plus preview and thumbnail. A real client Experience runs 30–50 MB.

A desktop visitor viewing ten Scenes pulls about 22 MB; a mobile visitor about 2 MB. That ratio is why the mobile tier matters, and it is the number that will determine CDN cost.

The finding that mattered most

Panorama processing was originally running inside the request. Measured on a 5952px panorama: 43.7 seconds for an HDR recipe, of which 41.5 seconds was a single CLAHE pass over the 6144px desktop variant. That was the reported "30–50 second" Studio freeze.

Three commonly-assumed causes were investigated and ruled out with measurements: cache invalidation was already narrowly scoped, manifest compilation runs only on publish and preview, and the heaviest database loader takes 23ms cold and 3ms warm.

Processing now runs on a queue. Apply returns in about 50ms, and the Studio stays responsive while a render proceeds.

What this closes

Studio responsiveness is no longer a problem to solve. Remaining optimisations that were on the list — replacing full refreshes with finer-grained updates — are not worth the churn at 241ms for the heaviest page. The public viewer's 169ms is the number object storage and a CDN will actually move, and it moves through geography and edge caching rather than application code.

14The migration plan

Target: Railway running two services from one repository, Supabase for database, storage, queue and auth, Sentry for monitoring. 

One codebase, one commit, one domain model
├── web service      Studio, Portal, viewer, APIs
└── worker service   panorama and media processing

Supabase (separate staging and production projects)
├── PostgreSQL       drafts, users, analytics, audit
├── Storage + CDN    originals private, derivatives public
├── Queues (pgmq)    durable media jobs
└── Auth             identity only; authorization stays in the app

The two services differ only in start command and allocated resources. This is one modular monolith running as two processes — not a microservice split.

PHASE 0

Freeze and measure Complete

Work committed and tagged. Restorable backup taken and verified. Production performance recorded as the baseline every later phase is measured against.

PHASE 1

Safety net Next

Nothing here depends on a hosting decision. This is what actually produces "no errors in production".

  • CI: typecheck, lint, unit tests, production build, E2E smoke
  • Golden manifest comparison — compile a fixture, diff against approved output
  • Authorization isolation — client A must never reach client B's Experience
  • Separate staging environment
  • Sentry in web and worker; structured logs; uptime checks
  • Gate the unsupported navigation presentations
  • Temporary login rate limiting
PHASE 2

Compute foundation Planned

Dockerise. Deploy web and worker as separate services from the same image. Health endpoints, deployment and rollback. The worker splits out now, not later — the evidence for it is already measured.

PHASE 3

Storage Planned

A storage interface with local and Supabase implementations passing the same contract tests. Originals private, derivatives and manifests public via CDN, content-addressed names, browser-direct uploads. Migrate existing files and verify every manifest reference resolves.

PHASE 4

PostgreSQL and durable queue Planned

The largest phase. Convert repositories to async, create the schema, migrate data, validate counts and relationships, and compare compiled manifests before and after — the strongest possible proof that nothing changed. Then cut the worker over to queue consumption, with idempotent jobs that survive a crash mid-render.

PHASE 5

Auth Planned

Deliberately after PostgreSQL. Roles, memberships and capabilities are application data; migrating identity first would require a temporary bridge from Supabase users to SQLite records, then a second migration. Configure custom SMTP — the built-in mailer is for testing only.

PHASE 6

Operational hardening Planned

Migrations before activation, retry and dead-letter handling, queue-age alerts, rollback rehearsal, restore rehearsal, and load testing of the viewer and upload pipeline.

Division of responsibility after the migration

Supabase Auth establishes who the user is. The application continues to decide what they can do — the capability matrix, client membership, Studio-versus-Portal routing, data isolation, user disabling and audit logging all stay in application code. Row Level Security is deliberately not adopted: two authorization systems that must agree is a liability, not a safety net.

15Where it goes

The milestone that defines readiness

Upload a panorama; process it through a durable worker; publish an immutable Experience; a visitor completes it and submits a genuine enquiry; the client sees that enquiry in their Portal; deploy a new version; then restore both data and media from backup after a simulated failure.

When that passes in staging, the system is ready for a controlled production pilot. Every element of it exists today except the enquiry — which is why lead capture is the highest-value product work after the infrastructure lands.

After that

  • Lead capture — the commercial loop. Configurable actions, consent, notifications, real enquiries in the Portal.
  • Session analytics — turn the existing event stream into visits, engagement, device mix and attribution.
  • Navigation presentations — build the six primitives the Studio already offers.
  • Localization and scene variants — the two features that most expand what an Experience can be.

What to protect

Three properties are worth defending as the system grows, because each is expensive to recover once lost:

  • The manifest boundary. The viewer must never read authoring state. It is what makes publishing safe and CDN delivery possible.
  • The repository boundary. Every database access through one layer. It is the only reason a database migration is tractable rather than a rewrite.
  • No inert controls. A setting that persists but changes nothing is worse than a missing feature — it teaches creators not to trust the panel. Trace every control to the code that reads it, or gate it.
